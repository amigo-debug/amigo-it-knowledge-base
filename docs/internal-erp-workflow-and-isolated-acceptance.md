# 內部 ERP：同頁分階段流程與隔離驗收

內部 ERP 的目標不是展示最多資料，而是讓員工在繁忙環境下知道**目前要做甚麼、下一步是甚麼，以及甚麼時候不可繼續**。當一個頁面同時包含太多表格與表單時，可保留同一路徑，但用工作階段把內容分開，減少捲動、誤觸與遺漏。

## 同頁分階段（Tabs）

「同頁分階段」是在同一頁用頁籤切換不同工作，例如服務明細、收款、成本、套票及結算。它與把功能拆成五個獨立頁面不同：使用者不會失去目前選取的客戶或結算項目，也不需要反覆返回上一頁。

| 設計原則 | 實際做法 | 好處 |
|---|---|---|
| 保留目前上下文 | 頁面頂部持續顯示目前客戶、工作或結算項目。 | 避免在不同階段處理錯誤對象。 |
| 一次只展示一個階段 | 非目前階段的長表單暫時收起。 | 縮短頁面並降低認知負擔。 |
| 顯示下一步 | 每個階段說明完成後應前往哪一階段。 | 新使用者不需要記住整套流程。 |
| 由伺服器核對規則 | 金額、權限及狀態限制不只依賴畫面按鈕。 | 即使前端操作出錯，資料仍受保護。 |

## View-first（先查看，後修改）

View-first 是指資料頁預設只能查看，使用者按「修改資料」後才可輸入或提交。這適合客戶、財務及正式文件等容易因誤觸造成影響的頁面。

提示列應保持緊湊，只需要清楚顯示「正在查看」或「正在修改」，不應在每個頁面重覆放置大型安全說明。高風險操作仍需要額外確認，例如完成服務、作廢文件或合併資料。

## 手機摘要卡與桌面表格

桌面適合密集表格，手機則適合每項一張摘要卡。兩者可以讀取同一份資料，但採用不同排列。

預約及服務工作在手機至少應保留：服務時間、客戶、病人姓名、服務個案、服務人員、狀態及金額。不能為了縮短畫面而隱藏前線判斷所需資料，也不應要求使用者橫向拖拉才能看到主要按鈕。

## RBAC 與最小權限

RBAC（Role-Based Access Control）是「按角色分配權限」。畫面隱藏按鈕並不等於安全，真正限制必須放在伺服器。

例如，前線服務人員只能完成本人獲派工作；系統管理員可在有實際服務紀錄時代為完成。這種規則要同時檢查角色、登入帳戶與派工關係，不能只相信前端傳入的服務人員編號。

## 原子交易（Atomic Transaction）

原子交易代表一組資料更新要麼全部成功，要麼全部不寫入。例如「完成服務並扣減服務套票」包含兩件事：更新服務狀態，以及扣減套票餘額。如果餘額不足，兩件事都應取消，不能出現服務已完成但套票未扣減的半完成狀態。

> 原則：涉及金額、餘額、狀態鎖定或多個資料表的操作，應優先使用原子交易。

## 409 資料衝突

HTTP 409 Conflict 表示請求格式沒有錯，但與現有資料衝突。例如使用者嘗試再次新增相同姓名及職位的使用中服務人員，系統應回覆清楚原因，並引導使用現有項目，而不是顯示「伺服器故障」。

防重覆應先定義可比較的識別方式。例如比對前先清除頭尾空白、把多個空格合併，並統一英文大小寫。若業務允許同名同職位人士，則應改用員工編號或其他真正唯一的欄位。

## 隔離端對端驗收

端對端驗收（End-to-End Acceptance Test）是以接近真實操作的方式，從流程起點一直走到終點。測試資料必須明確標示為「測試」，不得含真實姓名、電話、電郵或機構資料；測試電郵可使用 `example.invalid` 保留網域。

建議順序如下：

| 階段 | 驗收內容 |
|---|---|
| 1. 建檔 | 建立測試客戶、病人及服務個案，確認關係正確。 |
| 2. 預約 | 驗證依賴選單、日期防呆、確認預約及單一服務工作。 |
| 3. 派工 | 驗證人員去重、登入帳戶連結及主要服務人員。 |
| 4. 完成服務 | 驗證再次確認、角色範圍及可選套票扣減。 |
| 5. 財務 | 驗證服務金額、收款、分配上限及完成結算鎖定。 |
| 6. 文件 | 驗證草稿、確認鎖定、測試傳送、列印及作廢重開。 |
| 7. 操作紀錄 | 確認每項重要操作可追溯至登入使用者、時間及對象。 |

除了成功流程，亦要測試失敗分支，例如無效日期、重覆資料、越權完成、分配金額過高、餘額不足及已鎖定資料修改。失敗後要檢查資料庫沒有部分寫入。

## 品質閘門

| 術語 | 白話解釋 |
|---|---|
| TypeScript 檢查 | 檢查程式使用的資料型別是否互相配合。 |
| Lint | 檢查程式是否有容易出錯或不一致的寫法。 |
| Unit Test | 自動測試個別規則，例如金額計算或角色判斷。 |
| Production Build | 以正式部署方式編譯，及早發現只在正式版本出現的問題。 |
| Responsive Verification | 分別檢查桌面、平板及手機，而不是只縮小瀏覽器便當作完成。 |

上述檢查不能互相取代。單元測試通過，不代表按鈕排位正確；畫面看起來正常，也不代表伺服器權限與交易安全已被驗證。最終報告應分開列出每一類證據及尚未驗證的範圍。
